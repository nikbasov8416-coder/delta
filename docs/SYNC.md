# Синхронизация — этап 4

В настройках разблокированного приложения: на первом устройстве — «Создать
синхронизацию», на следующем — «Подключиться». Нужны OAuth-токен Яндекс Диска
с доступом только к папке приложения и общая парольная фраза (от 12 символов).
Перед подтверждением приложение предупреждает: потеря фразы означает невозможность
восстановления с Диска. Фразу следует сохранить в менеджере паролей.

Если на втором устройстве есть места хранения, слепки либо пользовательские
справочники или изменения стандартных справочников, предлагается выбор:
**заменить данными с Диска** (по умолчанию) или объединить по времени изменений.
Замена требует явного подтверждения; локальные незагруженные изменения будут
удалены. Сначала приложение читает и проверяет весь журнал, затем одной транзакцией
заменяет финансовые данные. PIN, биометрия, автоблокировка и защита экрана остаются
прежними. Нетронутые валюты и уровни ликвидности по умолчанию пользовательскими
данными не считаются: на чистом устройстве выбора и предупреждения о замене нет. Чистое устройство восстанавливает все синхронизируемые таблицы из журнала.

## Доступ к хранилищу

`SyncDisk` в `lib/data/sync/sync_storage.dart` — независимый контракт хранилища:
mkdir, read, list прямых детей, publish неизменяемого готового файла, close.
Пути логические; контракт публикации требует атомарности, идемпотентного повтора
тех же байтов и отказа при других байтах по существующему имени.
Журнал и криптография не зависят от транспортного протокола. Конкретный
адаптер выбирается фабрикой в провайдере. С 2026-11-17 по решению владельца
используется `YandexDiskRest`; `YandexWebDav` оставлен в исходниках и тестах для
возможного тарифа 360, но в интерфейсе больше не предлагается.

### REST/OAuth

REST API — только `https://cloud-api.yandex.net/v1/disk/`, заголовок
`Authorization: OAuth <токен>`. Логический `/Apps/Finance/` отображается в `app:/`
(папку OAuth-приложения), например `meta` — `app:/meta`, каталог журнала —
`app:/log/`. Право приложения — только `cloud_api:disk.app_folder`.
Папку Apps вручную создавать больше не нужно. Содержимое прежней WebDAV-папки
не переносится и не удаляется автоматически: это другой физический каталог.
Журнал, Argon2id/AES-GCM, meta и формат пачек **не изменены**.

Кнопка «Войти через Яндекс» показывает ссылку с копированием для браузера —
без новой зависимости url_launcher. В браузере пользователь подтверждает доступ,
копирует полученный токен и вставляет его в скрытое поле Delta. Пароль Яндекса
и пароль приложения в Delta больше не вводятся. OAuth implicit flow:
`https://oauth.yandex.ru/authorize?response_type=token&client_id=9dfd06f99533434999c25fc578b45663&force_confirm=yes`.
ClientID публичный, client secret не используется. Автоматического перехвата
callback/токена и локального HTTP-сервера нет.

Токен и производный ключ с meta хранятся одним объектом в secure storage
с признаком provider=yandex-rest-v1. Парольная фраза не сохраняется. Старый формат
login/password считается ненастроенной синхронизацией: сеть не вызывается,
старое значение, база, очередь и курсоры сами по себе не изменяются.
После обновления нужно заново настроить REST-подключение.

Операции адаптера:

- mkdir — PUT resources; уже существующая директория подтверждается отдельным
  GET метаданных (чтобы не принять обычный файл или другой HTTP 409 за папку).
- list — GET resources со страницами limit/offset, именем, типом, размером и временем изменения прямых детей.
  Имена возвращаются без путей и не могут содержать traversal/разделители.
- read — GET resources/download, затем GET выданного href. HTTP 404 означает null.
- publish — сравнение существующих байтов, GET resources/upload с overwrite=true,
  PUT по href в уникальный `.<uuid>.part`, затем POST resources/move с
  overwrite=false. Уникальные временные имена исключают смешивание двух
  одновременных публикаций meta; видимые имена готовых файлов прежние.
  Конфликт MOVE перепроверяет готовый файл; идентичные байты — успех,
  отличающиеся не перезаписываются.
- HTTP 202 — опрос операции до success/failed, с общим лимитом 30 секунд.
  Ссылка операции принимается только внутри API `/v1/disk/operations/`.

Ссылки передачи принимаются только по HTTPS (порт 443, без userinfo/fragment)
на поддоменах `*.yandex.net` и `*.yandex.ru`. **OAuth не передаётся по href**,
даже если href указывает на хост API. API-редиректы запрещены; редиректы передачи
проверяются заново на каждом шаге, максимум три. GET допускает обычные коды
редиректа, PUT — только 307/308, сохраняющие метод и байты. Чужие хосты отвергаются
до запроса. TLS не ослаблен; URL, токен и текст внешних ответов не журналируются.

HTTP 401 — «Вход в Яндекс истёк или отозван. Войдите заново»;
402 — ограничение операции по условиям тарифа; 403 — нет доступа к папке
приложения; 507 — недостаточно места. Сеть и тайм-аут различаются, прочие
HTTP-коды показываются без тела и URL. Один HTTP-запрос — до 30 секунд,
соединение — до 10, файлы/ответы — до 8 МиБ. Страницы списка, цепочка редиректов
и опрос операции также имеют отдельное общее окно 30 секунд.
При следующем открытии, возврате, сохранении или по кнопке выполняется новая попытка.

## Формат и шифрование

- `/Apps/Finance/meta`: format=1, UUID набора данных, Argon2id v19,
  memory=19456 КиБ, iterations=2, parallelism=1, случайная соль 16 байт,
  AES-256-GCM и зашифрованная проверочная строка. Параметры при чтении строго
  проверяются до запуска KDF; произвольно большие значения не принимаются.
- Argon2id выполняется в отдельном isolate, производный ключ — 32 байта.
  Проверочная строка аутентифицирует также параметры meta. Неверная фраза
  отклоняется до изменения данных и локального подключения.
- `/log/<device_id>/<20-значный номер>.bin`: nonce 12 байт, ciphertext,
  GCM tag 16 байт. Nonce случайный для каждого нового шифрования.
  AAD связывает файл с UUID набора данных, устройством и номером пачки.
  Внутри зашифрованный JSON: format, dataset, device, number и entries
  (`table`, полная `row`). Эти поля проверяются повторно после расшифровки.
- До 300 записей и 8 МиБ на пачку. `format` в meta и пачках оставляет место
  для будущего изменения формата и снимков `/state`; сжатие журнала и удаление
  старых пачек в этапе 4 **не выполняются**.

Яндекс видит имена/количество/размеры файлов, соль и параметры KDF, но не строки
финансовой базы. PIN, биометрия, время блокировки и FLAG_SECURE не попадают в
пачки. Синхронизируются currency, liquidity_level, storage, storage_currency,
snapshot, snapshot_line, snapshot_rate, audit_log, **rate_cache**. Таблица settings
пока целиком локальная: общих настроек приложения в ней ещё нет.

## Локальный журнал и восстановление после обрыва

Версия SQLite — 4. Предметные таблицы прежние; добавлены локальные sync_local,
sync_outbox и INSERT/UPDATE-триггеры. Изменение строки и полная запись в outbox
происходят в одной транзакции SQLite, включая кэш и надгробия. При каждом открытии
триггеры пересоздаются по текущим колонкам таблиц. Несовпадение набора колонок
входящей записи со схемой показывает отдельную ошибку другой версии Delta
с предложением обновить приложение; база и курсоры не меняются. При обновлении
с v3 имеющиеся строки однократно попадают в outbox. Вся база и локальная очередь
остаются под SQLCipher. Обратная установка старой программы после миграции не
поддерживается без восстановления старой копии базы.

До сети сохраняются номер, последний seq outbox и точные зашифрованные байты
ожидающей пачки. Загрузка пишет только `.part`, затем перенос без перезаписи публикует
законченное имя. Читатели игнорируют `.part`. При потере ответа на перенос/публикацию
повторяется тот же номер и тот же шифротекст. Уже существующий идентичный файл
считается успехом, отличающийся не перезаписывается. ACK удаляет отправленную
часть outbox и двигает номер одной транзакцией; более новые правки сохраняются.
Намерение создать meta и ключ тоже сохранены до первой публикации: неудачное
первоначальное создание можно продолжить после перезапуска приложения.

Входящие пачки читаются непрерывной последовательностью; пропуск номера — ошибка.
После проверки всех новых файлов применение и курсоры всех устройств обновляются
одной транзакцией с отложенными FK. Ошибка любой строки/файла не оставляет
частично применённых данных и не продвигает курсор. Повторные пачки безопасны.
Для каждой записи выигрывает лексикографически больший HLC; UUID устройства
в HLC разрешает равенство физических часов и счётчика. Надгробия сохраняются,
полученные HLC наблюдаются локальными часами. Применённые удалённые строки не
попадают повторно в outbox.

У производных строк (storage_currency, snapshot_line, snapshot_rate, rate_cache)
совпадение составного UNIQUE при разных UUID также сливается по HLC; локальный UUID
сохраняется. Если независимо созданные валюты имеют один код и разные UUID,
приложение останавливает применение
без частичных изменений и предлагает переименовать валюту или выбрать замену.
Автоматически перепривязывать ссылки таких записей оно не пытается.

## Запуск синхронизации и проверки (обновлено в части A)

После PIN/биометрии и при возврате — полный обмен. Фиксация слепка запускает
полный обмен сразу; остальные сохранения только попадают в outbox. В настройках
показывается «Есть неотправленные изменения». Кнопка запускает полный обмен.
На Android hidden/paused запускает неблокирующую отправку непустой очереди;
на Windows закрытие разблокированного окна при очереди/обмене показывает
«Синхронизация… приложение закроется» и ждёт не более 15 секунд. Ошибка не
удерживает окно. Пустое или заблокированное окно закрывается сразу.

Блокировка интерфейса происходит сразу, но освобождение HTTP/базы ждёт уже
начатую передачу не дольше 15 секунд, затем обрывает соединение; pending сохранён.
Нативные жизненный цикл Android и закрытие Windows требуют проверки владельцем.

## Обновление входа и смена фразы (часть A)

«Обновить вход в Яндекс» проверяет новый токен чтением активного meta: dataset,
check и параметры совпадают с сохранёнными. Затем меняется только token в secure
storage и выполняется обмен. Чужой dataset отклоняется до изменений. Очередь,
курсоры и ключ проверкой входа не сбрасываются. При незавершённой смене фразы
также признаётся уже опубликованный собственный новый набор из сохранённого намерения.

Новые синхронизации имеют format=2 и раскладку `sets/<dataset>/meta`,
`sets/<dataset>/log/<device>/<номер>.bin`; маленький `current` содержит format=2
и dataset. SyncDisk.replace атомарно меняет только служебные файлы (REST: .part
и MOVE overwrite=true; WebDAV: .part и MOVE Overwrite:T). Готовые пачки неизменяемы.
SyncDisk.delete ограничен syncRoot; REST DELETE resources permanently=true с
опросом 202, WebDAV DELETE. Корень целиком удалять нельзя.

Существующая синхронизация format=1 в корне продолжает читаться и записываться
без переподключения: новые приложения не переносят её автоматически. Перед
сменой фразы — обязательный полный обмен с ней. Предупреждение:
«Сначала синхронизируйте остальные устройства, их неотправленные изменения иначе
потеряются». Новая фраза вводится дважды и подтверждается. Старую фразу вводить
не нужно: рабочее устройство уже хранит производный ключ.

Новый dataset/соль/ключ сначала сохраняются как намерение в secure storage.
В SQLCipher сохраняются зашифрованные готовые пачки снимка, граница outbox и
прогресс. Новый набор целиком публикуется, затем атомарно переключается current.
Только после этого принимается новый ключ и чистятся прежний набор/старые .part.
Финансовые таблицы не заменяются; более новые локальные правки остаются в outbox.
Потеря ответа и перезапуск возобновляют тот же план/байты. Прерванная смена имеет
отдельную кнопку продолжения; повторный ввод другой фразы не меняет сохранённое
намерение. Сжатие обычного журнала по-прежнему не реализовано: снимок используется
только для новой синхронизации при смене ключа.

При первом переходе с legacy старый root/meta заменяется маркером format=2,
а прежний root/log удаляется после переключения. Старые установленные выпуски
останавливаются на своём сообщении «Неподдерживаемый или повреждённый формат
синхронизации»; изменить текст уже установленной программы невозможно. Данные
нового набора они не читают и не перезаписывают. Обновлённые устройства со старым
ключом получают «Синхронизация на Диске пересоздана. Подключитесь с новой парольной
фразой». Справка «Редкие ситуации» напоминает обновлять Delta на всех устройствах.

Все автоматические проверки используют выдуманные данные, отдельные базы SQLite
и fake-хранилище/HTTP-клиент. Живые запросы к Яндексу не выполняются.
Настоящие Windows/Android и два устройства проверяются владельцем после ревью Claude.

## Отключение на устройстве и обслуживание журнала

«Отключить синхронизацию на этом устройстве» удаляет локальный OAuth-токен,
производный ключ, курсоры и очередь. При неотправленных изменениях можно
сначала синхронизировать. На Диске при отключении ничего не удаляется.
Финансовые данные доступны на устройстве. Если отключение прервётся после
сохранения намерения, приложение завершит его при следующем запуске.
Затем снова доступны «Подключиться» и «Создать синхронизацию».

Если после отключения или восстановления нужно опубликовать локальную базу
вместо действующего набора на Диске, выберите «Подключиться → Заменить данными
этого устройства». Delta проверяет действующую фразу, публикует новый набор
из местной базы и переключает указатель после полной загрузки. Прежний набор
удаляется после переключения. Другие устройства нужно подключить заново.
Обычные варианты замены данных устройства и слияния доступны по-прежнему.

При полном обмене число и размер готовых `.bin` берутся из тех же страниц
списка журнала, которые нужны для получения пачек. Отдельных запросов размера
на каждую пачку нет. Учитываются загруженные в том же обмене пачки.
В активном `sets/<dataset>/` приложение удаляет только временные `.part`,
чьё время изменения строго старше 24 часов. Проверяются корень набора,
каталог журнала и папки устройств. Свежие файлы и готовые пачки сохраняются.
Неудачное удаление фиксируется в журнале приложения и обмен продолжается.

Сжатие журнала не выполняется по решению владельца от 2026-11-18. При двух
устройствах и редких слепках риск потери данных выше пользы. Смена парольной
фразы уже публикует свежий набор с текущим содержимым базы.
